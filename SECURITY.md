# Seguridad

## Principios

1. **El asistente nunca tiene más permisos que la persona.** Todas las consultas van a Supabase con el token del usuario y la clave anónima; **no existe clave service-role**. RLS es la frontera real; el servidor añade comprobaciones de rol por encima, nunca en lugar de RLS.
2. **Credenciales solo en el equipo de la persona.** Los tokens se guardan **cifrados** (AES-256-GCM) en `~/.config/chispa-mcp/credentials.json` con permisos 0600 (carpeta 0700). La clave se deriva de `vault.key` (aleatoria, 0600) y del identificador de la máquina, por lo que el archivo copiado a otro equipo no se puede leer. Un archivo ilegible o manipulado se ignora y se pide iniciar sesión de nuevo; `chispa-mcp logout` borra ambos archivos. Nada se envía a terceros: solo al proyecto Supabase.
3. **Mínimo de datos.** Las herramientas devuelven nombres y cifras; nunca correos, teléfonos ni datos de pago.
4. **Errores sin detalle técnico.** Al cliente le llegan mensajes en español; los detalles internos no salen del servidor.

## Controles

| Riesgo                                                | Control                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Token falsificado o de otro proyecto                  | Lo emite el endpoint OAuth del propio proyecto (se rechaza cualquier metadato fuera de su origen) y Supabase lo valida en cada consulta; credenciales de otro proyecto no se reutilizan                                                                                                                                                                                                   |
| Código de autorización interceptado                   | PKCE S256, `state` aleatorio, callback solo en `127.0.0.1`, un solo uso y tiempo máximo de 5 minutos                                                                                                                                                                                                                                                                                      |
| Cuentas anónimas o de estudiantes                     | Se rechazan tokens anónimos; cada herramienta exige `profiles.role` profesor o admin y cuenta no bloqueada                                                                                                                                                                                                                                                                                |
| Escalada entre aulas o roles                          | `classroom_id` obligatorio en toda herramienta de aula; rol resuelto en cada llamada y recordado hasta 20 s (`administrador` / `profesor`; RLS sigue decidiendo qué datos ve); los IDs recibidos se comprueban contra el aula                                                                                                                                                             |
| Texto de otras personas como orden (prompt injection) | Las instrucciones del servidor ordenan tratar chats y contenido como información; las respuestas con texto de estudiantes llevan una nota explícita; las acciones destructivas exigen `confirm: true` tras la confirmación de la persona                                                                                                                                                  |
| Inyección y contenido malicioso                       | Esquemas zod en cada herramienta; texto plano sin etiquetas; Markdown sin elementos activos (`script`, `iframe`, `svg`, `template`…), manejadores `on*`, `srcdoc`, ni enlaces `javascript:`/`data:`/`file:` (también dentro de atributos); limpieza repetida contra etiquetas anidadas; caracteres invisibles y de dirección eliminados; tope de longitud **antes** de procesar y después |
| Bucle del modelo que escribe sin parar                | Tope de escrituras por minuto (`CHISPA_WRITES_PER_MINUTE`); las cargas masivas son todo-o-nada y se pueden probar con `dry_run`                                                                                                                                                                                                                                                           |
| Página de login suplantada o reutilizada              | El callback solo atiende `127.0.0.1`/`localhost` con el puerto exacto (contra DNS rebinding), un solo uso, `state` obligatorio y CSP cerrada; cada fallo tiene su página de error                                                                                                                                                                                                         |
| Abuso                                                 | Límite de 256 KB por mensaje y sin lotes JSON-RPC; el límite por usuario lo aplican Supabase y RLS                                                                                                                                                                                                                                                                                        |
| Fuga por stdout                                       | Stdout es solo protocolo; auditoría y errores van a stderr                                                                                                                                                                                                                                                                                                                                |
| Exposición en tránsito                                | Solo HTTPS hacia Supabase                                                                                                                                                                                                                                                                                                                                                                 |
| Trazabilidad                                          | Registro de auditoría local por llamada (herramienta, resultado, duración) con usuario y aula **seudonimizados** con HMAC-SHA-256 y una semilla que solo vive en el proceso                                                                                                                                                                                                               |
| Acciones irreversibles                                | Las herramientas que escriben se marcan `readOnlyHint: false` y piden al asistente confirmar con la persona                                                                                                                                                                                                                                                                               |

## Revocar el acceso

`chispa-mcp logout` borra la sesión local. Para revocar el acceso, la persona retira la autorización en su cuenta (Supabase Auth). Al expirar el token de acceso y fallar la renovación, el acceso termina.

## Quién puede usar este paquete

El paquete y su código son públicos, pero **no da acceso a nada por sí solo**. Para usarlo hay que iniciar sesión con una cuenta registrada en Chispa:

1. El inicio de sesión pasa por la pantalla de consentimiento de la plataforma, que solo deja autorizar a cuentas de **docente o administrador no bloqueadas**. Estudiantes, cuentas anónimas y cuentas bloqueadas quedan fuera.
2. Cada herramienta vuelve a comprobar el rol de la persona (docente, administrador del aula, creador del curso) antes de actuar, y la base de datos aplica sus propias reglas (RLS) con el token de esa persona. La clave que incluye el paquete es la clave publicable de Chispa (la misma que usa el sitio web): sin sesión solo permite lo que las reglas de la base de datos ya dejan ver a cualquier visitante, como el catálogo público.
3. No hay claves de servicio ni secretos en el paquete ni en el repositorio. Los tokens de sesión viven solo en el equipo de quien inició sesión.

## Reportar una vulnerabilidad

Usa **«Report a vulnerability»** en la pestaña _Security_ de este repositorio (reporte privado de GitHub). No abras un issue público con detalles explotables. Responderemos con un plazo y, si procede, publicaremos una versión corregida y un aviso.
